# Протокол HTTP API

> [!abstract] Кратко
> Программный интерфейс для взаимодействия систем через [[Протокол_HTTP]]. Клиент шлёт запрос (метод + URL + данные), сервер отвечает (статус + данные). В основе — CRUD-операции и стиль REST.

## 1. Зачем нужно
Чтобы программы могли общаться между собой без участия человека. Мобильное приложение запрашивает список товаров, сайт отправляет данные в платёжную систему, Telegram-бот получает сообщения — всё это работает через API.

## 2. Простыми словами
API — это **меню в ресторане**. Ты (клиент) не заходишь на кухню (сервер), не трогаешь продукты. Ты смотришь в меню (документация API), выбираешь блюдо (метод и endpoint) и делаешь заказ (HTTP-запрос). Официант приносит результат (ответ). Кухня сама решает, как готовить — тебе важен только результат по оговорённым правилам.

## 3. Технические детали

### 3.1. Методы HTTP и CRUD
CRUD — четыре базовые операции над данными. Каждая соответствует HTTP-методу.

| Метод HTTP | Операция CRUD | Что делает | Пример |
|---|---|---|---|
| POST | Create | Создать новый ресурс | Отправить новый пост, зарегистрировать пользователя |
| GET | Read | Прочитать ресурс | Получить профиль, список товаров |
| PUT | Update (замена) | Заменить ресурс целиком | Перезаписать профиль полностью |
| PATCH | Update (модификация) | Обновить часть ресурса | Изменить только email в профиле |
| DELETE | Delete | Удалить ресурс | Удалить пост, отписаться |

> [!warning] PUT vs PATCH
> `PUT` заменяет объект **целиком** (что не передал — обнулится). `PATCH` меняет **только указанные поля**. Перепутаешь — потеряешь данные.

### 3.2. Структура запроса и ответа
- **Запрос:** URL (endpoint) + метод + заголовки (`Authorization`, `Content-Type`) + тело (Body, обычно JSON).
- **Ответ:** статус-код (`200 OK`, `201 Created`, `400 Bad Request`, `401 Unauthorized`, `404 Not Found`, `500 Internal Server Error`) + заголовки + тело (JSON).

### 3.3. Сложности и стандарты
- **Нет единого подхода:** каждый API уникален. Стандарт **REST** (архитектурный стиль) и OpenAPI/Swagger (документация) помогают унифицировать.
- **Авторизация:** OAuth 2.0, API-ключи, JWT-токены.
- **Версионирование:** версия в URL (`/v1/`, `/v2/`), чтобы обновлять API, не ломая старых клиентов.

### 3.4. Примеры популярных API
- YouTube Data API, HeadHunter API, VK API, Telegram API.

## 4. Пример / команда
- **GET-запрос через curl:**
    `curl -X GET "https://api.example.com/v1/users?limit=5" -H "Authorization: Bearer TOKEN"`
- **POST-запрос с JSON:**
    `curl -X POST "https://api.example.com/v1/users" -H "Content-Type: application/json" -d "{\"name\":\"Иван\"}"`
- **Postman:** графический инструмент для тестирования API (коллекции, окружения, автотесты).
- **DevTools браузера:** вкладка **Network** → фильтр **Fetch/XHR** (показывает запросы сайта).

## 5. Для ИБ

| Риск | Что делает атакующий | Защита |
|---|---|---|
| BOLA / IDOR (Broken Object Level Authorization) | Меняет ID в URL (`/users/1` → `/users/2`) и читает чужие данные. | Проверка прав на **каждый** объект, а не только на роль. |
| Broken Authentication | Подбирает токены, ключи, слабую авторизацию. | OAuth 2.0 + JWT, короткий TTL токенов, MFA. |
| Mass Assignment | Передаёт лишние поля (например, `"is_admin": true`), которые сервер слепо записывает. | Белые списки полей (allowlist), явная валидация. |
| Отсутствие Rate Limiting | Брутфорс, парсинг, DoS. | Rate limiting (`429 Too Many Requests`), капча, WAF. |
| Утечка через ошибки | Сервер отдаёт stack trace, внутренние пути, SQL-ошибки. | Единый формат ошибок без деталей, логирование на сервере. |
| Небезопасный транспорт | Перехват токенов и данных по HTTP. | Только HTTPS/TLS ([[Протокол_HTTPS]]), HSTS. |

**Главная мысль:** API — это открытая дверь в систему. Если авторизация проверяет только «кто ты», но не «что тебе можно» — жди BOLA. OWASP API Security Top 10 — твой следующий шаг.
